## 1. What this test proves

The pieces were built and tested one feature at a time. This Issue adds the one test that walks the whole product the way a user would, with no mocks and no direct database writes: an owner publishes a survey, a student answers it once, and the owner reads the aggregate, then reloads and sees the same numbers. It also gives AC-34 (the owner summary page) its automated test, which F-05 assigned to this Issue as TEST-38.

No production code changes in this Issue. The journey runs against the existing pages and API, so there is no red run before an implementation: the tests are checked for sensitivity instead, by breaking the code on purpose and saving the failing output (`docs/sprints/sprint-1/evidence/I-10-mutation-checks.txt`).

## 2. Rules the journey relies on

- Only the seeded fixture accounts are used: `ann.lee@classpulse.test` (owner of CPE334), `student1@classpulse.test` and `student2@classpulse.test` (enrolled in CPE334). The password comes from `SEED_PASSWORD`, never from a file in Git.
- Every run creates its own surveys with a run-unique title, so repeated runs never collide. Sprint 1 has no delete route, so these accumulate in the development database.
- The summary page shows aggregates only: the page text must not contain the respondent's name or email (AC-33 seen from the browser).
